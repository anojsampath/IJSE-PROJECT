Movie Ticket Booking
User Guide

Run the backend on Windows, sign in, manage screenings, and demonstrate seat booking and simulated payments.

This is a REST API, not a graphical movie-booking website. Use PowerShell or an API client such as Postman. Opening the server address in a browser does not display a booking screen. Payments are simulated; no real money moves.

1. Start on the configured PC

Open PowerShell in the project folder containing pom.xml and scripts. File Explorer's address bar can be used to enter powershell. These instructions use Windows PowerShell 5.1 or later.

If .local/credentials.clixml exists here, keep using that folder. Do not initialize it again. If the file is missing, follow section 2 first.

Terminal 1: MySQL

.\scripts\Start-LocalMySql.ps1

Start it only if this project's MySQL is not already running. Keep the terminal open. The configured database normally listens on 127.0.0.1:3306.

Terminal 2: Application

.\scripts\Start-LocalApp.ps1

Wait for Started MovieBookingApplication. The local API normally uses http://127.0.0.1:8081. The script prints the configured address, loads encrypted credentials, and starts the built JAR or the bundled JAR.

Terminal 3: Verify connectivity and sign-in

.\scripts\Test-LocalApi.ps1

Expected: PASS messages for anonymous access returning 401, administrator sign-in, and authenticated user/movie lists. This default check does not create or change business records.

Do not start a second API process if the first is running. You can check listening ports without stopping anything:

Get-NetTCPConnection -State Listen |
    Where-Object { $_.LocalPort -in 3306,8081 } |
    Select-Object LocalAddress,LocalPort,OwningProcess

2. Set up an extracted ZIP

  1. Install a Java 21 JDK. Confirm java -version reports version 21.
  2. Install MySQL Server 8.4; Workbench alone is not sufficient. The helpers use its installed binaries, with a separate project-owned data directory. They do not change another database or install a Windows service.
  3. Extract the ZIP completely to a writable local folder. Open the inner movie-booking folder, not the ZIP preview. Avoid a network/shared folder. Open PowerShell there.
  4. If Windows blocks the downloaded scripts, inspect their contents first, then unblock the trusted scripts:
    Get-ChildItem .\scripts\*.ps1 | Unblock-File
    If local script execution is still blocked, a session-only policy can be used on a PC you manage:
    Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
    Do not change machine-wide policy or override an organization's policy.

The ZIP intentionally contains no credentials, accounts, database files, Java installation, or MySQL installation. Each new extraction needs its own initialization. Do not copy another PC's .local folder: credentials are encrypted for the original Windows account and computer.

Step A: Initialize once

.\scripts\Initialize-LocalMySql.ps1

Default installation: C:\Program Files\MySQL\MySQL Server 8.4. If that path differs, or another application already uses port 3306 or 8081, choose unused ports at initialization:

.\scripts\Initialize-LocalMySql.ps1 `
    -MySqlHome 'C:\Program Files\MySQL\MySQL Server 8.4' `
    -DatabasePort 3307 -ApplicationPort 8082

Use one initialization command, not both. Existing local data/credentials are never overwritten. The chosen ports are saved and reused by the helper scripts.

Step B: First MySQL startup (Terminal 1)

.\scripts\Start-LocalMySql.ps1 -FirstStart

Keep this terminal open. First startup creates isolated movie_booking and movie_booking_test databases and accounts.

Step C: First application startup (Terminal 2)

.\scripts\Start-LocalApp.ps1 -BootstrapAdmin

The included app/movie-booking.jar runs without Maven or a dependency download. For a source checkout with no JAR, load the environment and run .\mvnw.cmd verify first; building requires internet access on the first run. Flyway creates application tables automatically. Do not import the migration SQL manually.

Step D: Verify and finish setup (Terminal 3)

.\scripts\Test-LocalApi.ps1
. .\scripts\Use-LocalEnvironment.ps1
.\mvnw.cmd verify -Pintegration

Require successful administrator sign-in and passing MySQL integration tests to verify both database accounts. After success, use File Explorer to delete .local/mysql-bootstrap.sql: it is a temporary plaintext setup file and must never be shared. Do not use -FirstStart again.

Stop the API with Ctrl+C in Terminal 2, then run .\scripts\Start-LocalApp.ps1 without -BootstrapAdmin. The administrator remains in the database. Future sessions use section 1 only.

Already managing your own MySQL database? Use the manual database and environment instructions in README.md, then run java -jar app/movie-booking.jar. The local helper scripts require their generated local configuration and are not used in that manual setup.

3. Sign in and use the API

The local administrator is admin@example.com, with a randomly generated password stored using Windows encryption. There is no shared default password.

In a new PowerShell terminal, run the following. The leading dot and space before the environment script are important: they load its values into the current session.

. .\scripts\Use-LocalEnvironment.ps1
$base = "http://127.0.0.1:$env:PORT/api"
$login = @{
    email = $localConfig.AdminEmail
    password = (ConvertFrom-LocalSecret $localConfig.AdminPassword)
}
$session = Invoke-RestMethod -Method POST -Uri "$base/auth/signin" `
    -ContentType 'application/json' -Body ($login | ConvertTo-Json)
$login = $null
$headers = @{ Authorization = "Bearer $($session.token)" }
Invoke-RestMethod -Uri "$base/movies" -Headers $headers

These commands do not print the password or token. Keep both private. Tokens expire after one hour; sign in again when a request returns 401.

Using Postman or another API client

  1. Register a customer with POST /api/auth/signup, JSON body containing name, email, and a password you choose. Passwords must be at least eight characters and at most 72 UTF-8 bytes. Signup always creates CUSTOMER.
  2. Send POST /api/auth/signin with your email and password.
  3. Use the returned token as a Bearer token in the client's Authorization tab. Do not export a collection or screenshot containing live credentials.
  4. Use the configured base URL, normally http://127.0.0.1:8081. Set request bodies to raw JSON and Content-Type: application/json.

Example customer-registration JSON (replace the sample credentials with your own):

{
  "name": "Sample Customer",
  "email": "customer@example.com",
  "password": "ChooseYourOwnPassword123!"
}

Use the administrator PowerShell session above for catalog management. The complete endpoint table and request examples are in README.md.

4. Demonstrate a complete booking

With MySQL and the API running:

.\scripts\Test-LocalApi.ps1 -CreateDemo

This option creates persistent, uniquely labeled demo records in the development database. It does not use real payments, delete existing data, or reveal credentials. Each run adds a customer, movie, theatre, show, booking, and payment; it finishes with the booking canceled and payment refunded. The generated customer's password is not retained for later sign-in; use your own customer account for manual demonstrations.

  1. Verify anonymous requests are rejected and the administrator can sign in.
  2. Create a demo movie, 52-seat theatre, and screening seven days in the future.
  3. Register a demo customer and reserve seats A1 and A2 at LKR 1,250.50 each.
  4. Verify the server-calculated total is LKR 2,501.00 and both seats are reserved.
  5. Create a SIMULATED payment, process a FAILED result, then retry successfully using the same payment ID.
  6. Verify the booking becomes CONFIRMED.
  7. Cancel the booking, verify REFUNDED payment status, and verify both seats are available again.

Expected: all checks report PASS, followed by IDs and final statuses. The sample screening remains in the catalog and can be used for manual bookings with your own customer.

Manual workflow

ActorActionEndpoint
ADMINCreate movie, theatre, then a future showPOST /api/movies, /api/theatres, /api/shows
CUSTOMERView available seatsGET /api/shows/{id}/seats
CUSTOMERReserve seatsPOST /api/bookings
CUSTOMERCreate and process paymentPOST /api/payments, POST /api/payments/{id}/process
Owner / ADMINView booking or cancel before startGET /api/bookings/{id}, PUT /api/bookings/{id}/cancel

Use returned IDs, not hardcoded IDs. A booking request contains showId, seatNumbers, and numberOfTickets. Payment creation contains bookingId and paymentMethod: "SIMULATED". Processing contains outcome: "COMPLETED" or "FAILED". Amounts are calculated by the server.

5. Roles and booking rules

  • ADMIN: manages users, movies, theatres, and shows; lists bookings/payments; can inspect and cancel customer bookings.
  • CUSTOMER: reads the authenticated catalog, books seats, pays for their own bookings, and views/cancels their own bookings.
  • Screening times use Asia/Colombo; prices are LKR. Shows cannot overlap in the same theatre, even across midnight.
  • Seats use ten positions per row: A1-A10, B1-B10, and so on; the final row is limited to theatre capacity.
  • PENDING and CONFIRMED bookings reserve seats. Reservations do not expire automatically in this version.
  • A seat map is a snapshot. A competing booking can still cause 409; reload available seats and select another seat.
  • A successful payment confirms the booking. Failed payments can be retried using the same payment ID. Completed/refunded payments cannot be processed again.
  • Canceling before show start releases seats and simulates a refund for completed payments. Canceled bookings cannot reopen.
  • Referenced records cannot be deleted. Preserve booking/payment history. Administrators cannot delete or demote their own account.

6. Tests and ZIP packaging

From the project root:

# Local unit and H2 workflow tests (no MySQL required):
.\mvnw.cmd test

# Full verification with an isolated MySQL test database:
. .\scripts\Use-LocalEnvironment.ps1
.\mvnw.cmd verify -Pintegration

# Verify formatting:
.\mvnw.cmd spotless:check

# Run verification and create a new ZIP:
.\scripts\Build-Distribution.ps1

The current suite contains 25 local tests and 16 MySQL integration tests, including concurrency, ownership, validation, and payment rollback. Reports are under target/surefire-reports and target/failsafe-reports. MySQL tests require the isolated movie_booking_test database and user. They retain test fixtures and must never target business data.

The packaging command requires successful formatting checks and all tests without skips. It creates a timestamped ZIP in dist plus a .zip.sha256 checksum. Inside the archive, DISTRIBUTION-MANIFEST.json records verification counts and SHA-256 hashes of each included file.

Compare Get-FileHash -Algorithm SHA256 -Path .\dist\<archive-name>.zip with the accompanying checksum file after copying the ZIP. Do not manually compress the whole workspace: .gitignore does not protect secrets in arbitrary ZIP tools.

7. Troubleshooting

SymptomWhat to do
No webpage / 401 at the serverThere is no frontend. Run the API-check script, or sign in and send a Bearer token. An anonymous catalog request returning 401 is expected.
Java not found / class version errorInstall/select Java 21 and reopen PowerShell. Check java -version.
Local configuration missingMake sure you opened the original configured folder; a new extraction needs section 2. Do not initialize over existing data.
Port already in useCheck whether this project's server is already running. Do not stop unrelated software. For a fresh installation, choose unused ports in the initializer.
MySQL connection refusedStart MySQL in Terminal 1 and confirm its configured port. Run the environment helper in the same shell as a manual Java/Maven command.
MySQL access denied / first setup incompleteConfirm the correct project folder and Windows user. First initialization needs -FirstStart once. Inspect .local/mysql-error.log privately. If initialization failed, preserve the folder and diagnose the error; do not blindly rerun initialization or first-start SQL.
Cannot decrypt credentialsDPAPI credentials belong to their original Windows account and PC. For another computer use a fresh extraction and fresh setup, not copied credentials.
401 after successful useSign in again; the JWT expires after one hour. A deleted account or changed signing key also invalidates access.
403 ForbiddenUse the required role or the booking's owner account. A customer cannot manage catalog records or inspect another customer's bookings.
400 / 404 / 409400: check JSON and validation field errors. 404: use an existing returned ID. 409: check seat occupancy, scheduling overlap, lifecycle restrictions, or referenced history.
JAR missingRe-extract the complete ZIP, or run .\mvnw.cmd verify from the source root. The launch helper checks target first, then app.
Maven download failsCheck internet/proxy access to Maven Central and Java configuration. Maven is bundled through the Wrapper; no global Maven installation is required. Offline JAR execution still requires installed Java and running MySQL.
Flyway / Mockito warningsThe current dependency set can warn about MySQL 8.4 being newer than Flyway's verified version and Mockito dynamic-agent attachment. These warnings did not prevent the verified test run. Actual migration errors or failing tests require investigation.

8. Stop, restart, and protect data

  1. Stop the API first using Ctrl+C in its dedicated terminal.
  2. Stop MySQL using Ctrl+C in its dedicated terminal. Wait for the process to exit; do not force-kill it while saving data.
  3. For the next session, start MySQL and then the API using section 1. Do not use initialization or first-start switches again.

Data survives normal restarts in .local/mysql-data. Do not delete or replace that directory to fix an application issue. Back up valuable data with approved database tools. The ZIP is a software distribution, not a backup of your bookings.

Keep .local, decrypted passwords, JWTs, and private logs out of email, Git, and shared ZIPs. Local helpers bind to loopback only; do not expose this development setup directly to the internet. Remote deployment requires HTTPS, verified database TLS, secure secret management, and a real payment provider.

Technical details, the ERD, all endpoints, and future expansion proposals are in README.md. GitHub publication is a separate action; generating this ZIP does not commit or push code.
